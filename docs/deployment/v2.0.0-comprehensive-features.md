## 1. Priority Preemption ✅

### Overview

Priority preemption allows high-priority jobs to preempt lower-priority running jobs to free up worker resources.

### Configuration

**Job Priority Levels:**
```yaml
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: critical-migration
spec:
  operation: convert
  image:
    path: /data/production-vm.vmdk
    format: vmdk

  # Priority: 0-100 (higher = more important)
  priority: 100  # CRITICAL

  # Preemption policy
  preemptionPolicy: Lower  # Can preempt lower priority jobs
```

**Priority Levels:**
- `100` - CRITICAL (preempts anything)
- `75` - HIGH (preempts NORMAL and below)
- `50` - NORMAL (default)
- `25` - LOW (can be preempted easily)
- `0` - BACKGROUND (preempted first)

**Preemption Policies:**
- `Never` - Never preempt other jobs
- `Lower` - Preempt only lower priority jobs (default)
- `SameOrLower` - Preempt same or lower priority
- `Always` - Preempt any job (CRITICAL only)

### How It Works

1. High-priority job enters queue
2. No workers available
3. Operator finds running jobs with lower priority
4. Lowest priority job is cancelled (preempted)
5. Worker becomes available
6. High-priority job assigned

**Example:**
```yaml
# Critical job preempts background job
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: urgent-fix
spec:
  priority: 100
  preemptionPolicy: Lower
  # ...

# This low-priority job will be cancelled
---
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: background-conversion
spec:
  priority: 0
  preemptionPolicy: Never
  # ...
```

### Monitoring

```promql
# Preemption rate
rate(hyper2kvm_operator_preemptions_total[5m])

# Jobs by priority class
count by (priority_class) (hyper2kvm_operator_jobs_total)

# Preemption candidates available
hyper2kvm_operator_preemptable_jobs
```

## 2. Auto-scaling Workers ✅

### Overview

Horizontal Pod Autoscaler (HPA) automatically scales worker pools based on queue depth, CPU, and memory utilization.

### Configuration

```bash
# Apply HPA
kubectl apply -f k8s/worker/worker-hpa.yaml
```

**HPA Configuration:**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hyper2kvm-worker-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hyper2kvm-worker
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        averageUtilization: 70

  - type: Pods
    pods:
      metric:
        name: hyper2kvm_operator_queue_depth
      target:
        averageValue: "3"  # Scale when queue > 3 jobs per worker

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
      - type: Percent
        value: 100        # Double worker count per minute
        periodSeconds: 60

    scaleDown:
      stabilizationWindowSeconds: 300  # Wait 5 min before scaling down
      policies:
      - type: Pods
        value: 1
        periodSeconds: 120
```

### Scaling Behavior

**Scale Up Triggers:**
- Queue depth > 3 jobs per worker
- CPU > 70% average
- Memory > 80% average

**Scale Down Triggers:**
- Queue depth < 1 job per worker
- CPU < 30% average for 5 minutes
- Memory < 40% average for 5 minutes

### Monitoring

```bash
# Check HPA status
kubectl get hpa hyper2kvm-worker-hpa -n hyper2kvm-system

# Monitor scaling events
kubectl describe hpa hyper2kvm-worker-hpa -n hyper2kvm-system
```

## 3. Advanced Retry Logic ✅

### Overview

Sophisticated retry mechanism with exponential backoff, failure thresholds, and retry budgets.

### Configuration

```yaml
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: resilient-migration
spec:
  operation: convert
  image:
    path: /data/vm.vmdk
    format: vmdk

  retryPolicy:
    maxRetries: 5
    backoff: exponential  # exponential, linear, or fixed
    baseDelaySeconds: 10
    maxDelaySeconds: 3600

    # Non-retryable errors
    nonRetryableErrors:
      - "invalid vmdk format"
      - "permission denied"
      - "quota exceeded"

    # Failure threshold
    failureThreshold:
      windowMinutes: 60
      maxFailures: 3  # Max 3 failures in 60 minutes

    # Immediate retry for transient errors
    immediateRetryErrors:
      - "worker unavailable"
      - "temporary network error"
```

### Backoff Strategies

**Exponential (default):**
```
Retry 1: 10s
Retry 2: 20s
Retry 3: 40s
Retry 4: 80s
Retry 5: 160s
```

**Linear:**
```
Retry 1: 10s
Retry 2: 20s
Retry 3: 30s
Retry 4: 40s
Retry 5: 50s
```

**Fixed:**
```
All retries: 10s
```

### Monitoring

```bash
# Check retry status
kubectl get migrationjob my-job -o jsonpath='{.status.retries}'

# View next retry time
kubectl get migrationjob my-job -o jsonpath='{.status.nextRetryTime}'
```

```promql

rate(hyper2kvm_operator_job_retries_total[5m])

# Retry budget exhaustion

# Average retries per job
```

## 4. Cost & SLA Tracking ✅

### Overview

Track resource costs, monitor SLA compliance, and optimize spending.

### Cost Tracking

Jobs automatically track compute, storage, and network costs:

```yaml
status:
  cost:
    computeCost: 0.002400  # $0.0024 (CPU + Memory)
    storageCost: 0.000100  # $0.0001 (I/O)
    networkCost: 0.000050  # $0.00005 (Transfer)
    totalCost: 0.002550    # $0.00255 total
```

**Cost Rates:**
- CPU: $0.036/hour per core
- Memory: $0.0036/hour per GB
- Storage I/O: $0.10/GB
- Network Transfer: $0.05/GB

### SLA Configuration

```bash
# Define SLA in operator configuration
kubectl apply -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata:
  name: hyper2kvm-sla-config
  namespace: hyper2kvm-system

  sla-production.yaml: |
    name: production
    maxDurationMinutes: 120

    maxRetries: 3
    priorityThreshold: 75

  sla-standard.yaml: |
    name: standard
    maxDurationMinutes: 240
    targetSuccessRate: 0.95
    maxRetries: 5
    priorityThreshold: 50
EOF
```

## 7. Job Templating ✅

### Overview

Create reusable job templates with parameters for common migration workflows.

### Creating Templates

```yaml
apiVersion: hyper2kvm.io/v1alpha1
kind: JobTemplate
metadata:
  name: standard-vmdk-conversion
spec:
  description: "Standard VMDK to qcow2 conversion with offline fix"
  operation: convert

  parameters:
  - name: vmPath
    type: path
    description: "Path to VMDK file"
    required: true
    validation:
      pattern: "^/data/.*\\.vmdk$"

  - name: outputPath
    type: path
    description: "Output directory"
    required: true

  - name: compress
    type: boolean
    description: "Enable compression"
    default: "true"

  - name: priority
    type: integer
    description: "Job priority"
    default: "50"
    validation:
      min: 0
      max: 100

  template:
    image:
      path: "{{.vmPath}}"
      format: vmdk
    artifacts:
      output_path: "{{.outputPath}}"
      output_format: qcow2
      compress: "{{.compress}}"
    priority: "{{.priority}}"
    retryPolicy:
      maxRetries: 3
      backoff: exponential
```

### Using Templates

```bash
# Create job from template
kubectl apply -f - <<EOF
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: vm1-conversion
  annotations:
    hyper2kvm.io/template: standard-vmdk-conversion
    hyper2kvm.io/template-parameters: |
      vmPath: /data/vm1.vmdk
      outputPath: /data/converted
      compress: true
      priority: 75
spec:
  # Generated from template
  operation: convert
  image:
    path: /data/vm1.vmdk
    format: vmdk
  artifacts:
    output_path: /data/converted
    output_format: qcow2
    compress: true
  priority: 75
EOF
```

### Template Library

```bash
# List templates
kubectl get jobtemplates -n hyper2kvm-system

# Template details
kubectl describe jobtemplate standard-vmdk-conversion
```

## 8. Backup/Restore ✅

### Overview

Backup operator state for disaster recovery and migration between clusters.

### Creating Backups

```bash
# Manual backup
kubectl exec -it deployment/hyper2kvm-operator -n hyper2kvm-system -- \
  python3 -m hyper2kvm.operator.backup create --name manual-backup-20260130

# Automated backups (CronJob)
kubectl apply -f - <<EOF
apiVersion: batch/v1
kind: CronJob
metadata:
  name: hyper2kvm-backup
  namespace: hyper2kvm-system
spec:
  schedule: "0 2 * * *"  # Daily at 2 AM
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: hyper2kvm-operator
          containers:
          - name: backup
            image: hyper2kvm-operator:v2.0.0
            command:
            - python3
            - -m
            - hyper2kvm.operator.backup
            - create
            - --auto-cleanup
            - --keep-count
            - "10"
            volumeMounts:
            - name: backups
              mountPath: /var/lib/hyper2kvm/backups
          volumes:
          - name: backups
            persistentVolumeClaim:
              claimName: hyper2kvm-backups
          restartPolicy: OnFailure
EOF
```

### Restoring Backups

```bash
# List available backups
kubectl exec deployment/hyper2kvm-operator -n hyper2kvm-system -- \
  python3 -m hyper2kvm.operator.backup list

# Dry run (validate only)
kubectl exec deployment/hyper2kvm-operator -n hyper2kvm-system -- \
  python3 -m hyper2kvm.operator.backup restore \
    --backup-path /var/lib/hyper2kvm/backups/backup-20260130-020000.json.gz \
    --dry-run

# Restore
kubectl exec deployment/hyper2kvm-operator -n hyper2kvm-system -- \
  python3 -m hyper2kvm.operator.backup restore \
    --backup-path /var/lib/hyper2kvm/backups/backup-20260130-020000.json.gz \
    --namespace hyper2kvm-system
```

### Backup Contents

Backups include:
- All MigrationJobs
- All JobTemplates
- Operator ConfigMaps
- Metadata (timestamp, counts, size)

### Disaster Recovery

```bash
# 1. Backup from old cluster
kubectl exec -it deployment/hyper2kvm-operator -n hyper2kvm-system -- \
  python3 -m hyper2kvm.operator.backup create --name dr-backup

# 2. Copy backup file to new cluster
kubectl cp hyper2kvm-system/hyper2kvm-operator-xxx:/var/lib/hyper2kvm/backups/dr-backup.json.gz ./dr-backup.json.gz

# 3. Install operator on new cluster
helm install hyper2kvm-operator hyper2kvm/hyper2kvm-operator \
  --namespace hyper2kvm-system --create-namespace

# 4. Upload backup to new cluster
kubectl cp ./dr-backup.json.gz hyper2kvm-system/hyper2kvm-operator-xxx:/var/lib/hyper2kvm/backups/

# 5. Restore
kubectl exec deployment/hyper2kvm-operator -n hyper2kvm-system -- \
  python3 -m hyper2kvm.operator.backup restore --backup-path /var/lib/hyper2kvm/backups/dr-backup.json.gz
```

## Migration from v1.9.0 to v2.0.0

### Breaking Changes

1. **CRD Schema** - New fields added (priority, preemptionPolicy, cost, sla)
2. **Metrics** - New metric names for v2.0.0 features
3. **API Version** - Still v1alpha1 but with extended schema

### Upgrade Steps

```bash
# 1. Backup current state
kubectl exec deployment/hyper2kvm-operator -n hyper2kvm-system -- \
  python3 -m hyper2kvm.operator.backup create --name pre-v2-upgrade

# 2. Update CRDs
kubectl apply -f k8s/operator/crds/migrationjob.yaml
kubectl apply -f k8s/operator/crds/jobtemplate.yaml

# 3. Upgrade operator
helm upgrade hyper2kvm-operator hyper2kvm/hyper2kvm-operator \
  --namespace hyper2kvm-system \
  --version 2.0.0 \
  --reuse-values

# 4. Apply HPA (optional)
kubectl apply -f k8s/worker/worker-hpa.yaml

# 5. Verify upgrade
kubectl get migrationjobs -n hyper2kvm-system
kubectl get jobtemplates -n hyper2kvm-system
kubectl get hpa -n hyper2kvm-system
```
