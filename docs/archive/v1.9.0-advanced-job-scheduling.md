## 1. Job Dependencies Overview ✅

### What Are Job Dependencies?

Job dependencies allow you to define execution order constraints between MigrationJobs:

```yaml
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: convert-disk-2
spec:
  operation: convert
  image:
    path: /data/vm2.vmdk
    format: vmdk
  dependsOn:
    - inspect-disk-1    # Wait for this job to complete
    - convert-disk-1    # And this one
```

### Key Concepts

**Directed Acyclic Graph (DAG):**
- Jobs form a directed graph where edges represent dependencies
- Graph must be acyclic (no circular dependencies)
- Execution flows from jobs with no dependencies to dependent jobs

**Execution States:**
- **Ready**: All dependencies completed successfully
- **Blocked**: One or more dependencies not yet completed
- **Failed**: One or more dependencies failed

### Architecture

```
┌─────────────────────────────────────────────────────────┐
│ MigrationJob CRD                                         │
│                                                          │
│ spec:                                                    │
│   dependsOn: [job1, job2]    ← Dependency declaration  │
│                                                          │
│ status:                                                  │
│   dependencies:              ← Dependency tracking      │
│     total: 2                                            │
│     completed: 1                                        │
│     failed: 0                                           │
│     blocking: [job2]                                    │
└─────────────────────────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│ Operator Controller                                      │
│                                                          │
│  ┌────────────────┐      ┌────────────────┐           │
│  │ Dependency     │      │ DAG Validator  │           │
│  │ Manager        │←─────│                │           │
│  │                │      │ - Cycle detect │           │
│  │ - Track deps   │      │ - Validation   │           │
│  │ - Check ready  │      │ - Topo sort    │           │
│  └────────────────┘      └────────────────┘           │
│           ↓                                             │
│  ┌────────────────┐                                    │
│  │ Job Assigner   │                                    │
│  │ - Check deps   │                                    │
│  │ - Assign if    │                                    │
│  │   ready        │                                    │
│  └────────────────┘                                    │
└─────────────────────────────────────────────────────────┘
```

## 2. Configuration ✅

### Defining Dependencies

**Simple Chain:**
```yaml
# Job A (no dependencies)
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: job-a
spec:
  operation: inspect
  image:
    path: /data/vm1.vmdk
    format: vmdk
---
# Job B (depends on A)
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: job-b
spec:
  operation: convert
  image:
    path: /data/vm1.vmdk
    format: vmdk
  dependsOn:
    - job-a
```

**Parallel Dependencies:**
```yaml
# Multiple jobs depend on same base job
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: final-job
spec:
  operation: offline_fix
  image:
    path: /data/vm-combined.qcow2
    format: qcow2
  dependsOn:
    - convert-vm1
    - convert-vm2
    - convert-vm3
```

**Complex DAG:**
```yaml
# Diamond dependency pattern:
#     inspect
#    /      \
# convert1  convert2
#    \      /
#   final-fix

# Base job
---
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: inspect-base
spec:
  operation: inspect
  image:
    path: /data/base.vmdk
    format: vmdk

# Parallel conversions
---
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: convert-disk1
spec:
  operation: convert
  image:
    path: /data/disk1.vmdk
    format: vmdk
  dependsOn:
    - inspect-base
---
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: convert-disk2
spec:
  operation: convert
  image:
    path: /data/disk2.vmdk
    format: vmdk
  dependsOn:
    - inspect-base

# Final fix depends on both conversions
---
apiVersion: hyper2kvm.io/v1alpha1
kind: MigrationJob
metadata:
  name: final-fix
spec:
  operation: offline_fix
  image:
    path: /data/combined.qcow2
    format: qcow2
  dependsOn:
    - convert-disk1
    - convert-disk2
```

### Dependency Constraints

**Valid:**
- ✅ No dependencies (standalone job)
- ✅ Single dependency
- ✅ Multiple dependencies
- ✅ Transitive dependencies (A→B→C)
- ✅ Diamond patterns (A→B,C→D)

**Invalid (Rejected):**
- ❌ Self-dependency (job depends on itself)
- ❌ Circular dependencies (A→B→A)
- ❌ Missing references (depend on non-existent job)

## 3. Dependency Validation ✅

### Automatic Validation

The operator automatically validates dependencies when a job is created:

**Validation Checks:**
1. **Existence Check** - All referenced jobs must exist
2. **Self-Dependency Check** - Job cannot depend on itself
3. **Cycle Detection** - DAG must be acyclic
4. **State Check** - Dependencies must be in valid states

**Example Validation Failure:**

```bash
# Try to create job with circular dependency
kubectl apply -f circular-job.yaml

# Job will fail validation:
kubectl get migrationjob circular-job -o yaml
```

```yaml
status:
  state: Failed
  result:
    success: false
    errorMessage: "Invalid dependencies: Circular dependency detected: job-a -> job-b -> job-a"
```

### Validation Metrics

Monitor validation failures:

```promql
# Total dependency violations by type
hyper2kvm_operator_dependency_violations_total{violation_type="cycle"}

# Cycle detection violations
hyper2kvm_operator_dependency_violations_total{violation_type="missing_ref"}

# Self-dependency violations
hyper2kvm_operator_dependency_violations_total{violation_type="self_dependency"}
```

## 4. Execution Flow ✅

### Job Lifecycle with Dependencies

```
1. Job Created
   ↓
2. Dependencies Registered
   ↓
3. DAG Validated (cycle check)
   ↓
4. Job Validated
   ↓
5. Job Queued
   ↓
6. Dependencies Checked
   ├─ All Completed → Assign to Worker
   └─ Some Incomplete → Wait (Blocked)
   ↓
7. Dependencies Complete → Transition to Assigned
   ↓
8. Job Running
   ↓
9. Job Completed → Unblock Dependent Jobs
```

### Dependency Status Tracking

Check dependency status:

```bash
kubectl get migrationjob my-job -o yaml
```

```yaml
status:
  state: Queued
  dependencies:
    total: 3
    completed: 1
    failed: 0
    blocking:
      - job-dependency-1
      - job-dependency-2
```

**Fields:**
- `total`: Total number of dependencies
- `completed`: Number of completed dependencies
- `failed`: Number of failed dependencies
- `blocking`: List of dependencies still blocking execution

### Execution Planning

The operator calculates execution levels for parallel execution:

```bash
# View execution plan via logs
kubectl logs -n hyper2kvm-system deployment/hyper2kvm-operator | grep "execution plan"
```

Example output:
```
Execution Plan (4 levels):
  Level 0: [job-a]                    (1 job can run)
  Level 1: [job-b, job-c]            (2 jobs can run in parallel)
  Level 2: [job-d, job-e, job-f]     (3 jobs can run in parallel)
  Level 3: [job-g]                    (1 job can run)
```

## 5. Failure Handling ✅

### Failure Propagation

When a job fails, dependent jobs can be automatically failed:

**Propagation Behavior:**
- Jobs in `Created`, `Validated`, or `Queued` state are failed
- Jobs already `Running` continue execution
- Jobs already `Completed` are not affected
- Transitive dependencies are also failed

**Example:**

```
job-a (FAILED)
  ↓
job-b (Queued) → FAILED (propagated)
  ↓
job-c (Queued) → FAILED (propagated)
```

### Checking Propagated Failures

```bash
# Check if job failed due to dependency
kubectl get migrationjob job-b -o jsonpath='{.status.result.errorMessage}'
```

Output:
```
Dependency failed: job-a
```

### Metrics

Track failure propagation:

```promql
# Total failures propagated
hyper2kvm_operator_dependency_failures_propagated_total

# Rate of failure propagation
rate(hyper2kvm_operator_dependency_failures_propagated_total[5m])
```

## 8. Troubleshooting ✅

### Issue: Circular Dependency Detected

**Symptoms:**
- Job stuck in `Failed` state
- Error message mentions circular dependency

**Diagnosis:**
```bash
kubectl get migrationjob my-job -o jsonpath='{.status.result.errorMessage}'
```

**Solution:**
1. Review dependency chain
2. Identify cycle in dependencies
3. Remove circular reference
4. Delete and recreate affected jobs

### Issue: Job Blocked Forever

**Symptoms:**
- Job stuck in `Queued` state
- Dependencies never complete

**Diagnosis:**
```bash
# Check blocking dependencies
kubectl get migrationjob my-job -o jsonpath='{.status.dependencies.blocking}'

# Check dependency states
for dep in $(kubectl get migrationjob my-job -o jsonpath='{.status.dependencies.blocking[*]}'); do
  echo "Dependency: $dep"
  kubectl get migrationjob "$dep" -o jsonpath='{.status.state}'
  echo ""
done
```

**Solution:**
1. Check if blocking jobs are running
2. Review blocking job logs for errors
3. Consider canceling and recreating blocked job

### Issue: Missing Dependency Reference

**Symptoms:**
- Job creation fails
- Error about non-existent dependency

**Diagnosis:**
```bash
kubectl get migrationjob my-job -o jsonpath='{.status.result.errorMessage}'
```

Output:
```
Invalid dependencies: Dependency not found: non-existent-job
```

**Solution:**
1. Verify dependency job exists
2. Check spelling of dependency name
3. Ensure dependency is in same namespace
4. Create dependency job first, then dependent job

### Issue: Unexpected Failure Propagation

**Symptoms:**
- Jobs failed without being assigned
- Error message mentions dependency failure

**Diagnosis:**
```bash
# Check if job failed due to propagation
kubectl get migrationjob my-job -o yaml | grep -A5 result
```

**Solution:**
1. Identify root cause of original failure
2. Fix failed dependency
3. Delete and recreate propagated failures
4. Jobs will execute once dependency completes

## 9. Best Practices ✅

### Dependency Design

**Do:**
- ✅ Keep dependency chains short (3-5 levels max)
- ✅ Maximize parallelism at each level
- ✅ Use descriptive job names showing relationships
- ✅ Group related operations in stages

**Don't:**
- ❌ Create overly complex DAGs (>50 jobs)
- ❌ Use dependencies for unrelated jobs
- ❌ Create unnecessarily deep chains
- ❌ Mix unrelated workflows in one DAG

### Performance Optimization

**Parallel Execution:**
```yaml
# Good: Parallel jobs
inspect-vm1, inspect-vm2, inspect-vm3  (3 parallel)
  ↓
convert-vm1, convert-vm2, convert-vm3  (3 parallel)
```

```yaml
# Bad: Sequential jobs (unnecessary)
inspect-vm1 → inspect-vm2 → inspect-vm3  (3 sequential)
  ↓
convert-vm1 → convert-vm2 → convert-vm3  (3 sequential)
```

### Resource Planning

Consider worker capacity when designing DAGs:

```yaml
# If you have 3 workers, design for 3-way parallelism
level1: [job1, job2, job3]     # 3 workers fully utilized
level2: [job4, job5, job6]     # 3 workers fully utilized
```

### Monitoring

**Essential Alerts:**
```yaml
# Jobs blocked for too long
- alert: JobBlockedTooLong
  expr: hyper2kvm_operator_dependency_wait_time_seconds > 3600
  annotations:
    summary: "Job waiting on dependencies for >1 hour"

# High circular dependency rate
- alert: CircularDependencies
  expr: rate(hyper2kvm_operator_dependency_violations_total{violation_type="cycle"}[5m]) > 0.1
  annotations:
    summary: "Circular dependencies being detected"

# Low parallelism utilization
- alert: LowParallelism
  expr: hyper2kvm_operator_dag_parallelism_potential / hyper2kvm_operator_dag_ready_jobs < 0.3
  annotations:
    summary: "DAG has low parallelism potential"
```
